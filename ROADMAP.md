# Roadmap / backlog

Направление: [видение PushIt](VISION.md). Приоритеты ниже задают порядок работы, а не сроки или обещание готовности. Критерии приёмки — цели будущих проверок; наличие команды само по себе не означает, что критерий выполнен.

## Текущая база

В `main` уже есть CLI `init`, `build`, `dev`, `deploy`, `verify`, `plan`, `status`, `logs`, `rollback`, `login` и профили подключений; скилл агента и шаблон приложения; WASM-runtime со статичным UI, keyvalue (встроенная NoSQL-БД приложения)/SQL/blobstore/logging host-интерфейсы. Root-манифест `apps:` синкает репозитории, собирает и деплоит приложения **на стороне клиента**, контроллер принимает артефакты. `pushit login` сохраняет API-токен: браузерный вход через Keycloak для OIDC или пароль владельца для standalone; это не refresh-токен.

В `main` также есть standalone owner auth полного контроллера без обязательных
Keycloak/Caddy: `local` ограничен HTTP loopback и `*.localhost`, а `builtin`
использует фиксированный внешний HTTPS base origin и reverse proxy на том же
хосте/в том же сетевом пространстве имён; backend — только числовой loopback HTTP.
Оба режима сохраняют хаб, поддомены приложений, деплои, версии и секреты;
это не `pushit dev` и не отдельный runtime без контроллера. Cookie host-only,
в builtin — Secure `__Host-`; owner CLI-токены действуют 30 дней, OIDC-токены —
примерно год. Login сохраняет токен в выбранный/активный профиль, без профиля —
в legacy-файл. OIDC остаётся Keycloak-специфичным путём.
Контракты и ограничения: [local](docs/standalone-local-auth.md),
[builtin/proxy](docs/standalone-proxy-auth.md). Протокольные проверки и nginx smoke
с реальным TLS не являются проверкой cookie-prefix enforcement в браузерном
движке; такая браузерная QA остаётся открытой.

Это описание реализованных поверхностей, не security/reliability sign-off. Изменения в открытых PR не считаются частью `main`. Текущие команды и ограничения: [README](README.md), [скилл](skills/pushit-app/SKILL.md), [архитектура](ARCHITECTURE.md).

## 1. Надёжность: auth → deploy → rollback

Стабилизировать существующий путь до добавления новых механизмов.

Критерии приёмки:

- Автоматические проверки подтверждают отказ без валидной аутентификации на защищённых API и приложениях; dev-bypass работает только при явном dev-режиме сервера, а не по присланному клиентом заголовку. Истёкшие/невалидные токены и подмена идентичности отклоняются.
- Успешный deploy даёт доступный UI и функцию `/_fn/*`; некорректный архив, манифест, компонент или отсутствующий секрет завершают deploy ошибкой без потери последней рабочей ревизии.
- После повторного deploy, ошибки deploy и перезапуска контроллера активная ревизия соответствует `status` и фактически обслуживаемому приложению.
- Rollback проверяется на двух различимых ревизиях: UI и функция возвращаются к выбранной ревизии, повторная проверка это подтверждает. Невалидная цель не меняет рабочее приложение.
- Проверки покрывают config/secrets/capabilities при смене ревизий; явно документировано, что rollback не откатывает данные БД и blobstore. Логи и ошибки позволяют понять причину сбоя без раскрытия секретов.

## 2. Агентский путь: скилл, шаблоны, CLI и проверка

После стабилизации базового пути сделать основной сценарий воспроизводимым для агента.

Критерии приёмки:

- Из чистого каталога по установленному скиллу агент проходит `init → build → deploy → status/logs → HTTP-проверка UI и функции`; инструкции совпадают с реальными командами и требуют только перечисленных зависимостей.
- Проверка проводится и с локальным dev-окружением, и с обычным аутентифицированным профилем; dev-путь не подменяет проверку auth.
- CLI однозначно сообщает выбранный инстанс, результат и ревизию, возвращает ненулевой exit code при ошибке. Частичный сбой root-деплоя называет неудачные приложения; повторный запуск имеет документированный результат.
- Шаблоны и скилл объясняют работу с секретами, диагностику и rollback. Успех команды деплоя отделён от проверки доступности и поведения приложения; агент не объявляет задачу завершённой без последней проверки.

Выбранный контракт CLI для этого: `pushit verify` — HTTP-проверки из `checks:`
манифеста с `--json` и ненулевым exit code при провале; фильтры
`pushit logs --since/--grep`. Расширение контракта — по подтверждённой потребности.

## 3. IaC: воспроизводимый перенос кода и конфигурации

Цель — поднять то же внутреннее приложение на другом хосте через манифесты и CLI, без ручного восстановления неописанных настроек.

Критерии приёмки:

- На втором чистом совместимом инстансе PushIt из зафиксированного исходного revision и манифестов воспроизводятся build, deploy, UI и функция.
- Перечислены зависимости: версии toolchain/runtime и draft-WASI интерфейсов, артефакты UI/WASM, env, имена секретов, SQL/blobstore-привязки, настройки домена и auth. Секреты предоставляются отдельно; скрытых зависимостей от первого хоста нет.
- Один документированный сценарий переноса проверяет итог через HTTP и показывает ограничения `plan` (сейчас это diff конфигурации, не доказательство совпадения кода/артефактов).
- Проверка явно использует новое/внешнее тестовое состояние: она не выдаётся за перенос БД, файлов или состояния платформы.

Текущая ограниченная регрессия: [два изолированных локальных инстанса](docs/portability.md). Она не заменяет проверку второго хоста и не закрывает все критерии выше.

Фиксация версий, формат комплекта переноса и автоматизация проверки требуют отдельного решения. Совместимость с произвольным WASM-хостом не обещается.

## Позже: данные, файлы и состояние

Миграция app-local key-value store (redb), внешних SQL-данных, blobstore и состояния контроллера — отдельный следующий объём, не условие завершения первых трёх приоритетов. До реализации нужны решения о границах экспорта, согласованности, резервных копиях, секретах, проверке восстановления и откате неудачной миграции. Цель приёмки: проверенный перенос тестового набора с подтверждением целостности; механизм пока не выбран.

Backup/restore платформы — ответственность инфраструктуры и оператора, не
команды CLI или API PushIt. Это относится и к SaaS-развёртываниям.

## Остальной backlog: по подтверждённой потребности

- Production/runtime-запуск приложения **без контроллера** — отдельная возможная потребность, не backlog уже реализованных standalone `local`/`builtin` режимов полного контроллера. `pushit dev` остаётся локальной отладкой, не production-контрактом. Отдельный бинарь на базе host-кода или другой совместимый runtime — варианты для оценки; предпочтительный вариант пока не выбран и требует отдельного архитектурного решения.
- Серверный git-poll/webhook. Сейчас root-манифест обрабатывает клиент; перенос build-команд на сервер требует отдельного архитектурного и security-решения.
- Фильтр хаба по Keycloak-группам, RBAC на приложения.
- Request-id correlation и фильтр уровня в `pushit logs`.
- Тёплый пул WASM-инстансов — только при измеренной проблеме latency.
- Cron/фоновые задачи — при появлении конкретного сценария. `wasi:keyvalue` (store) реализован как встроенная БД; atomics/batch/watch-интерфейсы и внешние kv-бэкенды (Redis) — при появлении конкретного сценария.
